What is youki?

Is a low-level OCI runtime written in Rust.
容器 — means “container” in Japanese.

  • Low-level OCI runtime — é a camada que realmente cria containers no Linux, falando diretamente com o kernel via namespaces e cgroups.
  • Escrito em Rust — memory safe sem garbage collector, performance no nível de C. Esse foi o principal motivador para reescrever o runc.
  • O nome 容器 significa "container" em japonês — uma referência cultural ao universo de containers.
  • Drop-in replacement para o runc — mesma interface CLI, mesmo OCI spec. Você troca literalmente sem mudar nada acima.
  • Funciona com Podman, Docker, containerd — nada na stack acima precisa mudar.

exploring config.json — the OCI container spec file

  • namespaces — This section tells youki which Linux namespaces to create for the container. Each entry is a type: "pid" means the container gets its own process tree (it can't see host processes), "network" gives it an isolated network stack, "mount" isolates the filesystem view, and "uts" gives it its own hostname. youki calls clone(2) with the corresponding flags for each one.
  • cgroups / resources — The "resources" block maps directly to cgroup settings. "memory.limit" of 536870912 = 512 MB max RAM. youki writes these values to the cgroup filesystem under /sys/fs/cgroup/. If the container exceeds the limit, the kernel OOM-kills it.
  • seccomp — This defines a syscall filter. "defaultAction: SCMP_ACT_ERRNO" means ANY syscall not explicitly listed will be blocked with EPERM. Then the "syscalls" array whitelists specific calls — here "read" and "write" are allowed. youki passes this profile to the kernel via the seccomp(2) syscall before execve().
  • The key insight — youki reads this single config.json file and orchestrates all three mechanisms together. The OCI spec defines what goes in the file; youki is what actually applies it to the Linux kernel.
  • --- LIVE DEMO SCRIPT ---
  • Step 1 — show seccomp is active inside the container: run: podman run --runtime youki --rm alpine grep Seccomp /proc/self/status → expect "Seccomp: 2" (2 = filter mode active, 0 = disabled).
  • Step 2 — try dmesg WITH seccomp (blocked): run: podman run --runtime youki --rm alpine dmesg → expect: "dmesg: read kernel buffer failed: Operation not permitted". Explain: dmesg calls the syslog(2) syscall (number 103 on x86_64) to read the kernel ring buffer. The default seccomp profile blocks it — containers should not read host kernel logs.
  • Step 3 — try dmesg WITHOUT seccomp (works): run: podman run --runtime youki --rm --security-opt seccomp=unconfined alpine dmesg → kernel log appears. Same container, same image, only difference is seccomp=unconfined. This proves it is seccomp doing the blocking.
  • Talking point: "Notice — same youki runtime, same alpine image, same dmesg command. The only change is removing the seccomp profile. That one JSON field in config.json is the difference between a container that leaks kernel information and one that does not."

The Borrow Checker in Action

// borrow checker prevents entire classes of security bugs at compile time
fn setup_namespaces(spec: &Spec) -> Result<()> {
    // compiler tracks ownership — ns cannot outlive spec
    let ns = spec.linux().namespaces();  // Option<&Vec<..>>
    for namespace in ns.iter().flatten() {
        unshare_or_setns(namespace)?;  // ? = propagate error up immediately
    }
    Ok(())
}
  • ? operator — propagates errors at every syscall; no silent failures
  • Ownership prevents use-after-free — enforced at compile time, not runtime
